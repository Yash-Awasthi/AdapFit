1. Storage God Object

Strong
core/storage.py core/repository.py core/database.py

Problem

StorageEngine is a 200-line God Object that handles 7 data types (users, baselines, recovery_logs, workouts, workout_logs, workload_history, agent_memory) with two parallel implementations in every method: in-memory dict + Supabase fallback via lazy import. The repository.py duplicates the same 7-type interface. Understanding one data type requires reading the entire 200-line file. There's no locality — changing how recovery logs are stored means touching a method buried between workout and agent memory methods.

Solution

Extract a StorageBackend protocol with get_user(), save_recovery_log(), etc. Create two adapters: InMemoryAdapter and SupabaseAdapter. Then split the God Object into domain-scoped stores: RecoveryStore, WorkoutStore, MemoryStore — each owns only its data type and delegates to the backend adapter.

Benefits

  • Locality: Changing recovery log storage only touches RecoveryStore
  • Testability: Each store can be tested with a mock backend adapter independently
  • Deletion test: Deleting WorkoutStore doesn't affect recovery or memory — concentrates complexity correctly
  • Leverage: Adding SQLite or Postgres direct adapter is one new class, not editing 20 methods

2. Recovery Score Duplication

Strong
services/recovery_engine.py services/agent/orchestrator.py core_engine/__init__.py services/workflow_engine.py

Problem

Recovery score is computed three separate ways: RecoveryEngine.compute_daily_recovery() (Pydantic-based), agent_orchestrator.execute_recovery_analysis() (dict-based, calls core_engine directly), and workflow_engine.morning_recovery() (also calls core_engine directly). Each recomputes the same HRV Z-score, sleep score, subjective score, and ACWR — but with slightly different default values and data access patterns. The orchestrator duplicates recovery_engine's work but also fetches from storage, creating a split-brain: pure function vs. storage-dependent function doing the same math.

flowchart TD

  R2 --> C2[core_engine functions]

  style R2 fill:#22c55e,stroke:#16a34a,color:#fff

Solution

Delete orchestrator.execute_recovery_analysis() entirely — it duplicates recovery_engine. The workflow_engine already calls core_engine directly (which is fine — it's a thin pipeline). The endpoint calls RecoveryEngine for pure computation + ml_engine for predictions. One path.

Benefits

  • Locality: All recovery math lives in one place (recovery_engine + core_engine)
  • Testability: RecoveryEngine is already tested — orchestrator's copy was never tested independently
  • Deletion test: Deleting orchestrator's recovery method concentrates, not scatters — the endpoint already does the same work

3. Endpoint Orchestration Bloat

Worth exploring
api/v1/endpoints/workouts.py api/v1/endpoints/recovery.py

Problem

complete_workout() in workouts.py is 80 lines of orchestration: compute Foster load → fetch history → EWMA → store workload → store log → NLP sentiment → agent memory → ML injury risk → return response. This is a use case, not an endpoint handler. The endpoint mixes HTTP concerns (request/response, status codes) with business logic (ACWR computation, NLP analysis, agent memory updates). Testing this requires spinning up the full FastAPI test client.

Solution

Extract a CompleteWorkoutUseCase class that owns the 80-line orchestration. The endpoint becomes 5 lines: parse request → call use case → serialize response. The use case can be tested with mocked storage/ml/nlp — no HTTP layer needed.

Benefits

  • Testability: Use case testable without FastAPI TestClient, with injected mocks
  • Leverage: Same use case callable from CLI, background job, or mobile app
  • Locality: All "complete workout" logic in one place, not scattered across endpoint

4. ML Engine Monolith

Worth exploring
services/ml_engine.py

Problem

MLEngine is a 200-line monolith combining 5 unrelated concerns: feature extraction, PyTorch neural net training/prediction, HRV forecasting (linear regression), anomaly detection (z-score), and injury risk scoring. Each method is shallow — the interface is nearly as complex as the implementation. The class holds mutable training state (is_trained, _feature_history) alongside stateless functions like detect_anomalies().

5. NLP Pipeline Mixed Concerns

Speculative
services/nlp_pipeline.py

Problem

NLPPipeline mixes 4 unrelated concerns: sentiment analysis (with HuggingFace + keyword fallback), exercise feedback extraction (pain detection), muscle group NER (synonym matching), and LLM-powered goal parsing + weekly summaries (Gemini API calls). The Gemini API calls are async, the sentiment is sync, and the muscle extraction is pure string matching — three different execution models in one class.

Solution

Split into: SentimentAnalyzer (sync, keyword-based), GoalParser (async, LLM-backed), MuscleExtractor (pure function, no class needed). The weekly summary generator is already thin enough to stay in the orchestrator or a small helper.

Benefits

  • Testability: MuscleExtractor is a pure function — trivial to test
  • Locality: LLM dependency isolated in GoalParser, not infecting sentiment analysis

🏆 Top Recommendation

Candidate 1: Storage God Object — tackle first.

The StorageEngine is the most tangled seam in the codebase. Every service, every endpoint, and every test touches it. Splitting it into domain-scoped stores with a backend adapter protocol would:

  • Unblock testing of every other candidate (they all depend on storage)
  • Create a real seam where the in-memory ↔ Supabase switch lives — currently it's scattered across 14 methods with lazy imports
  • Make the repository.py redundant (it duplicates the same interface)
  • Enable adding new storage backends (SQLite, Postgres direct) without touching 200 lines

After Candidate 1, Candidate 2 (recovery duplication) is the quick win — just delete the orchestrator's duplicate recovery method. Candidates 3-5 are deeper refactorings that become easier once storage is clean.
